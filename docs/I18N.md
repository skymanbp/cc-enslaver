# I18N — language version control (English is the skeleton)

> This document is the **manifest** for cc-enforcer's multi-language
> design. It declares the source-of-truth language, the translatable
> surface, how translations are kept in sync (a *hard*, CI-enforced
> check), and how to add a new language.

---

## Source of truth: English

**English is the skeleton language** — the source of truth for every
rule text and every injection prompt. Translations are first-class but
*follow* the skeleton. **If a translation ever drifts from the skeleton,
the English version wins**, and the drift is a CI failure to be fixed by
updating the *translation*, never by bending the skeleton to match a
translation.

"Content can be any language" — an individual project's Imperial Edicts
(`edicts.toml`) and the user's own prose are free-form and untracked.
Only the plugin's *own* rule/prompt surface is version-controlled here.

---

## Layout (asymmetric: skeleton at the canonical path)

```
rules/00-index.md, 01..12-*.md        # English skeleton  ← source of truth
rules/zh/00-index.md, 01..12-*.md     # Chinese translation
prompts/session-start.md, user-prompt.md      # English skeleton
prompts/zh/session-start.md, user-prompt.md   # Chinese translation
```

- Root-level `*.md` under a **skeleton root** (`rules/`, `prompts/`) is
  the English skeleton.
- Each immediate **subdirectory** (`zh/`, and any future `<code>/`) is a
  translation of that root, file-for-file.

**Guard output is the third skeleton surface (v0.38)**, and it is a dict
rather than a directory of files:

```
hooks/scripts/lib/messages_en.py      # English skeleton  ← source of truth
hooks/scripts/lib/messages_zh.py      # Chinese translation, same keys
hooks/scripts/lib/messages.py         # per-key resolution + fallback
```

Everything a guard *prints* — deny reasons, the nine-layer status table,
recovery blurbs, the plain-language line — lives here. Before v0.38 it was
hardcoded in the guards **and bilingual**: an English body with a Chinese
`大白话:` line appended and Chinese phrasings offered inline. Both READMEs
quoted real samples of that, so both READMEs mixed languages, accurately.

Two things differ from the markdown roots, both deliberate:

- **Storage.** These strings are read on *every* hook invocation, which sits
  in the critical path of the agent's tool calls. An import compiles once to
  `.pyc`; a markdown or TOML parse is paid every time.
- **Gate strength.** A dict can be compared on exact key sets *and* on the
  `str.format` fields each value carries. Markdown can only be compared on
  heading shape. See the sync contract below.

Resolution is **per key**, not per file: a translation missing a key yields
the English string for that key, so a half-finished translation is degraded,
never broken.

Edict UI chrome (the injected banner + DENY-reason headline) is *not*
files either but per-language string dicts in
[`hooks/scripts/lib/edicts.py`](../hooks/scripts/lib/edicts.py)
(`_INJECT_STRINGS`, `_DENY_REASON_TEMPLATES`), keyed by language code and
defaulting to `en`.

## Runtime resolution (`CC_ENFORCER_LANG`)

The injection language is chosen at runtime by the `CC_ENFORCER_LANG`
environment variable:

| `CC_ENFORCER_LANG` | Prompt read | Behaviour |
|---|---|---|
| unset / empty / `en` | `prompts/<file>` (root) | English skeleton (default) |
| `zh` | `prompts/zh/<file>` | Chinese translation |
| `<code>` (any) | `prompts/<code>/<file>` | that translation, **falling back** to the root English skeleton (with a stderr note) if the file is missing |

There is **no hardcoded language allow-list** — any code passes through.
An unknown or partially-translated language degrades gracefully to the
English skeleton rather than erroring. Set it persistently on Windows
with:

```powershell
[Environment]::SetEnvironmentVariable("CC_ENFORCER_LANG", "zh", "User")
```

The default (`en`) lives in exactly two places, both named `DEFAULT_LANG`:
[`inject_context.py`](../hooks/scripts/inject_context.py) (prompt lookup)
and [`lib/edicts.py`](../hooks/scripts/lib/edicts.py) (edict UI chrome).

### Detection is language-independent; the wording is not (v0.38)

Two different things, and the distinction is the whole design:

- **What the guards MATCH** is not coupled to `CC_ENFORCER_LANG` at all.
  `stop_guard` / `read_guard` / `bash_guard` detect completion, hedge and
  patch markers in **both** languages always. Switching the language does
  **not** weaken enforcement, and a `zh` session is never offered a smaller
  deny set than an `en` one — `i18n_check`'s enforcement-token parity exists
  because that had once been true by accident.
- **What the guards SAY** does follow `CC_ENFORCER_LANG`, as of v0.38. The
  same verdict, in your language.

So an English message may name only the English spellings of a marker set
that also accepts Chinese, and the Chinese message only the Chinese ones —
both are true statements about a bilingual detector. What is **not** allowed
is inventing a spelling: a message that names a marker the detector does not
match describes a detector that does not exist, which is the v0.35.1 defect
class. Check the live pattern set before writing the sentence.

## The sync contract (hard, CI-enforced)

The skeleton↔translation contract is enforced by
[`hooks/scripts/i18n_check.py`](../hooks/scripts/i18n_check.py), which
checks — for every translation subdir under every skeleton root:

1. **File-set parity** — every skeleton `*.md` has a same-named
   translation (`missing_file`), and the translation has no file the
   skeleton lacks (`orphan_file`).
2. **Section-structure parity** — for each shared file, the sequence of
   ATX markdown header levels (e.g. `[1, 2, 2, 3]`) must be identical.
   Header *text* is deliberately **not** compared (it is translated);
   only the structural skeleton — how many sections, at what depth, in
   what order — must match. `#` lines inside fenced code blocks
   (```` ``` ```` / `~~~`) are skipped so shell/YAML comments are not
   mistaken for headers.
3. **Enforcement-token parity** (v0.26) — on any line stating a physical
   enforcement outcome (`DENY` / `BLOCK` / `拒绝` / `拦截`), every backtick
   code span that looks like a command an agent would type must also appear
   somewhere in the translation (`enforcement_tokens`). Prose gets
   translated and structure is compared above, but the tokens an agent is
   *told will be denied* are not prose — they are the contract. Until
   v0.26.0 the Chinese injection listed four of the seven patterns
   `bash_guard` denies, so a `zh` session was handed a strictly smaller deny
   set than an `en` session on every turn, and checks 1 and 2 were both
   green. Two measured bounds keep it usable: only enforcement lines are
   scanned (comparing *every* code span flags 24 legitimate translation
   differences in `rules/`), and only machine-shaped tokens count (a first
   cut demanded translators reproduce English prose examples). It does
   **not** verify that the enforcement *sentence* survived translation —
   only that its tokens appear in the file.

For the **message catalogs** (v0.38) the same function runs a stronger set,
because a dict admits comparisons markdown does not
(`check_message_catalogs`):

4. **Key-set parity**, both directions — `missing_key` (untranslated, so the
   session would mix languages) and `orphan_key` (nothing reads it).
5. **Per-key placeholder parity** — the `str.format` fields in each value
   must match the skeleton's exactly. This is the one that bites at runtime:
   a translation that drops `{file_path}` still renders and silently tells
   the user less than the skeleton does, and one that invents a field raises
   `KeyError` inside the hook, at the moment the user is already being
   denied.
6. **Every key a guard asks for exists** — literal `messages.text("…")` calls
   plus the two computed families (per Stop layer, per bash pattern), which
   are expanded from the same source. A renamed key would otherwise only
   surface as `<<missing message: …>>` inside a live deny.

Checks 4–6 read only files that actually import the catalog. That filter had
to be assembled from concatenation: spelling out the import phrase made this
module itself look like a consumer, and the check reported that a guard was
requesting the key `a.b` — which is the example in its own docstring.

Run it directly, or via the slash command:

```bash
python hooks/scripts/i18n_check.py           # full report, exit 1 on drift
python hooks/scripts/i18n_check.py --quiet    # exit code only
```

```
/cc-enforcer:i18n
```

**Why this is a hard action, not soft docs:** `check_sync()` is asserted
by [`tests/test_i18n_sync.py`](../tests/test_i18n_sync.py)
(`assertEqual(check_sync(), [])`), which `unittest discover` auto-collects
into the existing GitHub Actions matrix (ubuntu + windows × Python 3.13).
Any structural drift between a translation and the English skeleton turns
CI red on every push/PR. That is what makes language version control satisfy the
project's own rule 07 (every requirement lands as a verifiable hard
action, not a documentation reminder). The same test suite also proves
the checker is not *vacuously* passing — it injects `missing_file`,
`orphan_file`, `header_structure`, and `enforcement_tokens` drift into
temp trees and asserts each is caught.

## Adding a language

To ship a new translation `<code>` (e.g. `ja`, `es`, `fr`):

1. **Create the translation dirs** mirroring the skeleton roots:
   `rules/<code>/` and `prompts/<code>/`.
2. **Translate file-for-file**, keeping the header-level structure of
   each file identical to the English skeleton (translate the header
   *text*, not the `#` nesting). Every skeleton `*.md` must have a
   same-named counterpart.
3. **(Optional) Add edict UI chrome** for `<code>` in
   [`lib/edicts.py`](../hooks/scripts/lib/edicts.py): a `<code>` key in
   `_INJECT_STRINGS` and `_DENY_REASON_TEMPLATES`. If omitted, edict
   chrome falls back to English (`.get(lang, ...["en"])`).
4. **Verify zero drift**: `python hooks/scripts/i18n_check.py` →
   "all translations in sync"; `python -m unittest discover tests` green.
5. **Use it**: `CC_ENFORCER_LANG=<code>`. Any file you haven't
   translated yet falls back to the English skeleton at runtime, so a
   language can be shipped incrementally — but CI stays green only once
   the file-set + structure parity is complete.

---

## On drift, English wins

When `i18n_check.py` reports drift, the fix is **always** to update the
translation to match the skeleton — add the `missing_file`, remove/justify
the `orphan_file`, or reshape the translation's sections to the skeleton's
header structure. Never edit the English skeleton merely to silence a
translation mismatch; the skeleton changes only when the *rule itself*
changes, and then every translation is updated to follow.
