# 规则 03 — 修根因，不修症状

## 原则

遇到错误、失败、异常时：**找原因，不掩盖**。绕过检查、屏蔽错误、用 sleep 掩盖竞态都是**技术债务**，不是修复。

## 上游溯源（v0.28）—— 你找到的第一个原因很少是根

原因是成链的，每个失败都有三种位置：

| 层级 | 是什么 | 修在这里算什么 |
|---|---|---|
| **症状位** | 失败浮出水面的地方——抛出的异常、错误的输出、红掉的测试 | 补丁 |
| **传播路径** | 坏状态在浮出水面之前流经的代码 | 仍是补丁 |
| **起源** | *产生*坏状态的机制 / 设计决策 / 缺失不变量 | 修复 |

三级可以重合：当起源*就是*症状位时，修在那里*就是*修起源。被禁止的
是没问过这个问题就停在表面。

问题出现时，**严禁**在症状位做点对点修补。强制次序是**溯源 → 确诊 → 修复**：

1. **沿链上爬。** 从失败出发，反复问"是什么产生了*这个*？"，直到答案
   是机制、设计决策或缺失的不变量——而不是又一个症状。每一跳都记
   `file:line` 证据（rule 05）。
2. **停在中途必须给出理由。** 真正的起源可能够不到——vendor 的 bug、
   平台契约、别人的仓库。这时修在更低的节点是合法的，但必须显式：
   点名真正的起源，并说明修复为何落在它的下游。不说明的中途停下，
   只是文书更齐全的补丁。
3. **动手前先确诊。** 用第一方证据——探针、复现、红测试——证明疑似
   起源确实产生了观察到的症状（rule 01）。没被证明过的诊断，是穿着
   白大褂的猜测。紧急止血可以先于完整确诊，但必须显式标注为"缓解"
   ——它是记录在案的债务（rule 07），绝不许被报告成修复。
4. **在确诊的起源处修一次**——一次统一修改，覆盖该起源产生的每一个
   实例（rule 09"一个根因，一次统一修复"）。

在本仓库自己身上的实测：v0.25.1 正确地*点名*了一条根因——检测器
描述的是"字符串"而不是"概念"——然后只修了它见过的实例。机制留了
下来，下一轮审计（v0.26）就发现同一类的新一批缺陷，其中包括一个
倒退。修机制缺陷的实例，就是高一层的修症状。

## 禁止的"反模式"清单

| 反模式 | 为什么是偷懒 | 应该做什么 |
|--------|-------------|-----------|
| `try: ... except: pass` | 静默吞掉错误，丢失诊断信息 | 让异常上抛 OR 在 except 里**记录并以正确方式处理** |
| `--no-verify` 跳过 git hooks | 钩子是为了拦住坏提交；跳过 = 提交了坏代码 | 修钩子失败的根本原因 |
| `time.sleep()` 修竞态 | 在快机器/慢机器上行为不同；治标不治本 | 修同步原语（锁、条件变量、await） |
| `// @ts-ignore` / `# type: ignore` | 类型系统报警是有原因的 | 修类型 OR 在注释里写**为什么**忽略 |
| `if (false)` 关闭测试 | 静默移除覆盖率 | 修测试 OR 删除测试并解释 |
| `pip install --force-reinstall` 解决冲突 | 没解决依赖图 | 解决依赖图，使用锁文件 |
| `chmod 777` 解决权限 | 制造安全洞 | 找出真正的所属用户/进程 |
| `rm -rf node_modules && reinstall` 当万能药 | 不知道究竟修了什么 | 找出哪个依赖坏了、为什么坏 |
| 把超时拉长 10 倍 | 把 latency bug 变成更慢的 latency bug | 找慢的原因 |
| 把测试的断言放宽 | 测试就此失去意义 | 修产品代码或修测试期望（明确二选一） |

## 必须做（MUST）

- 任何 `except` 块中：要么**记录后重抛**，要么**有明确的可恢复处理逻辑**并写一行注释解释 why。
- 任何 `--no-verify` 的使用：必须有用户**显式授权**（否则这是规则违反）。
- 任何 sleep / wait：必须**有明确的事件可等**，而不是"等够长"。
- 任何忽略类型 / lint 的注释：必须解释 **why** 这次忽略是合理的。
- 任何修复：先写出因果链——症状位 → 传播路径 → 起源——以及这次修改落在链上哪一级；未修到起源必须按上面"上游溯源"一节给出停下的理由。

## 自检触发器

下列任一情况出现，agent 应主动自检本规则：

- 即将写 `except: pass` / `except Exception: pass`；
- 即将写 `time.sleep(N)` 在测试或同步代码里；
- 即将加 `--no-verify` / `--force` / `--skip-*` 标志；
- 即将加 `@ts-ignore` / `type: ignore` / `# noqa`；
- 即将注释掉一个失败的测试；
- 即将"重新部署"或"重启服务"作为修复；
- 这个失败和以前修过的某个长得一样——这是"类"在自我宣告；沿链上爬，不要修补新冒头的这一处；
- 即将在抛错的那一行动手，而没有问"是什么产生了流到这里的坏状态"。

> 触发时正确的做法：**停下来**，回答规则 02 的"七问"，先理解机理。
